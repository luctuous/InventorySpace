How the app thinks

Before you touch anything, one idea is worth understanding, because everything else follows from it: every physical thing you own is an Item, and items are seen from four different heights.

ConceptWhat I need · “Black PLA filament”
AnalogousWhich options serve me interchangeably · “Black PLA filament 1.75 mm”
VariantWhat I actually buy · “Prusament PLA Black, 1 kg spool”
ItemWhich physical unit I hold · spool filamentAA007

The top three levels are catalogue: they describe things. Only the last level is reality: each Item is a concrete object you can pick up, with its own location, remaining quantity and price.

The golden rule: stock is never typed in

Nowhere in the app is there a box where you write “I have 4 kg of filament”. Stock is calculated by summing the remaining quantity of items that are in stock or open. If the number on Home doesn't match reality, the answer is always in the items: either one wasn't depleted, or one was never entered.

The hierarchy can be ignored

The four levels exist for when you need them, not to force you through them. With Quick Add you type a name, pick a type and a quantity, and the system quietly creates the Concept, the Analogous group and the Variant for you. You can run your whole inventory without ever opening those pages, and refine later if it ever matters.

Types are what make the app yours

A Type defines which custom fields its items carry, which statuses they may have, and whether they track a quantity. A model railway collector defines “scale” and “era”; a 3D-printing workshop defines “material” and “diameter”. Same app, no code changes.

If you would rather be shown than read

The ? at the bottom of the sidebar holds this manual and a set of guided tours. They point at the real screen, step by step, and take about two minutes each. Everything they show is written up here too — start with whichever suits you.

Starting up and signing in

In development

npm run dev

Starts both halves at once: the API on port 3001 and the web app on 5173. Open http://localhost:5173. Stop with Ctrl+C.

With Docker

docker build -t inventoryspace .
docker run -d -p 3000:3000 \
  -v ./inventory-data:/data \
  -e BETTER_AUTH_SECRET="$(openssl rand -base64 32)" \
  inventoryspace

Here everything runs on one port: http://localhost:3000 serves the web app, the API and the docs. Database migrations apply themselves at startup, so an empty volume works first time.

The first account

The sign-in screen has a link: “First run? Create the admin account”. The first account you register becomes the administrator, and public registration closes immediately afterwards. From then on, the administrator creates accounts from the Users page.

You sign in with a username, not an email. It is free-form: anna, Anna Müller, torn-nit, jm are all fine — letters, spaces and accents included. Capitals don't matter, so Anna and anna are the same person. The only things it cannot contain are an @, a double space, or spaces at the ends. An email address is optional and exists only so an account can be tied to a mailbox one day; nothing is ever sent to it.

Careful

If you don't set BETTER_AUTH_SECRET, the server generates a new one on every boot and everyone is signed out each time you restart. In development that's harmless; in production, set it.

Clearing the demo data

The development database ships with example data from a workshop: 5 types, a location tree, 6 concepts and 9 items, arranged so the Home screen shows all three alert states (fine, low stock, out of stock). To start on your inventory you have two routes.

Fast route: wipe everything at once

# stop the server first
rm packages/api/data/inventory.db*
npm run dev

Startup recreates the empty schema. Don't run npm run db:seed and you get a genuinely clean database: no types, no locations, no items. The first account you register becomes the administrator again.

Irreversible

This also deletes the user accounts and the entire history. Under Docker, the equivalent is emptying the ./inventory-data volume.

Manual route: delete from inside the app

If you'd rather do it by hand to see how it works, you have to go bottom-up. The app blocks any deletion that would leave things orphaned, and tells you exactly why:

To delete a…You must first…Otherwise
Conceptdelete its Analogous groups“N analogous group(s) still reference this concept”
Analogousdelete its Variants“N variant(s) still reference this analogous group”
Variantdelete its Items“N item(s) still reference this variant”
Typedelete the items of that type“N item(s) use this type”
Locationempty it and delete its children“N item(s) in this location or its sub-locations”

So the real order is: Items → Variants → Analogous → Concepts, then Locations (leaf to root) and Types.

No deletion is truly destructive: everything is a soft delete. The row stays in the database with a deletion timestamp and disappears from the lists. History is never deleted. Read before relying on this too much, because getting things back from the interface isn't easy yet.

Tutorial: building your inventory

Let's set up the inventory of a 3D-printing workshop from an empty database. It works just the same for a collection, a cosmetics workshop or a spare-parts store: only the names change.

  1. Define your Types

    This comes first because everything else depends on it. Go to Types (admin only) and press New type. Our workshop needs two deliberately different ones.

    Filament — something that gets consumed:

    • Name: “Filament”. The field has EN DE CA tabs: English is required, the others optional.
    • Key: filament. This is the internal identifier and can never be changed.
    • ID prefix: filament. Items will be named filamentAA001, filamentAA002…
    • Tracks a quantity: yes (a spool is used up gradually).
    • Valid statuses: in_stock, open, depleted, discarded.
    • Custom fields: press Add field three times: material (select, options PLA, PETG, ABS, TPU), color (text), diameter (number, unit mm).

    On the right, the Add-item form preview panel shows you live what the item form for this type will look like. It's how you check you've understood what you're defining before you save.

    Printer — a machine, which isn't consumed:

    • Key printer, prefix printer.
    • Tracks a quantity: no.
    • Valid statuses: in_service, maintenance, out_of_service, retired.
    • Custom fields: manufacturer (text), nextService (date).
    Its own statuses

    Items of this type are never «open» or «depleted» — their lifecycle is a different one. Their detail view carries a Set status dropdown holding exactly the statuses you defined.

  2. Map where things live

    Go to Locations. The tree has four fixed levels —workshop → room → zone → surface— but you choose the names; for a workshop, read them as building → room → cabinet → shelf.

    Press New workshop: the code L01 is already suggested, name it “Workshop”. Now hover over the row and a + appears to add a child: the next code is calculated for you too (L01R01). Build something like: 

    L01            Workshop
  L01R01       Print room
    L01R01Z01  Material cabinet
      ...S01   Shelf A
    L01R01Z02  Printer bench

    The number on the right of each row is how many items are in that node and everything below it. This tree isn't just labelling: on Home it doubles as a filter.

  3. Enter your first things

    Two paths from here. For the overwhelming majority of cases the right one is Quick Add: press the q key or the Quick Add button on Home, type “Prusament PLA Black”, pick the Filament type, a location, quantity 1, unit kg, and save. You now have the item, and the Concept, Analogous group and Variant were created for you.

    Do it a few times in a row: the dialog stays open with the name cleared and remembers the last type and location, because entering ten things back to back is the normal case.

  4. Refine the catalogue only if you need to

    Say you now buy black PLA from a second brand and you want the app to understand that either one will do. This — and only this — is the moment to open the catalogue pages:

    • Go to Variants and rename the one Quick Add created so it says the real commercial product: “Prusament PLA Black, 1 kg spool”. While you're there, fill in brand, supplier, catalogue ref, pack size and unit.
    • Press New variant, hang it off the same Analogous group, and put the other brand in.

    From now on the Concept's stock adds up both brands, and on Home you'll see them grouped under the same concept but on separate lines.

  5. Get warned before you run out

    Go to Concepts, edit “Black PLA filament” and set Min. stock to 2. From now on, when the total drops below 2 kg the Home card turns amber and expands itself. At zero, red. Without a threshold, a concept never warns you.

Quick Add, in detail

This is the path designed for when you're standing in the storeroom holding the thing. It opens with the q key (when you're not typing in a field) or the Quick Add button, present on both Home and Items.

The name field is a search box

As you type, matches appear underneath — across all languages at once — and what happens depends on what you pick:

  • You pick a Variant (they're listed first, they're the shortest path): the item hangs directly off that product. The type selector disappears, because the variant already knows its type.
  • You pick a Concept: it's noted as the reference for your search.
  • You pick nothing: on save, the system creates the Concept → Analogous → Variant chain using the name you typed, and hangs the item off it. It all happens in a single transaction: either everything is created, or nothing is.
Why it matters

This search box is the only thing standing between you and a database full of duplicates. It's worth typing three letters and glancing at the list before creating anything new.

The rest of the form

  • Type — remembers the last one you used.
  • Location — also remembered; opens the tree.
  • Quantity and unit — only take effect if the type tracks a quantity.
  • Price — write it however feels natural (22.40 or 22,40).
  • Copies — 1 to 100. If three identical spools arrive, put 3: you get three items with consecutive identifiers.
  • If the type has required custom fields, they appear here. Optional ones only show up in the full form.

On save, a toast confirms the identifiers created. If a new chain was created, the toast offers a Refine → link to Variants in case you want to add brand and supplier right away. If you don't, nothing breaks: refining is optional forever.

The life of an item

Click any row in Items and the detail drawer slides in from the right, with two tabs: Details and History. The actions sit at the top.

ActionWhat it actually doesMinimum role
Open Goes from in stock to open and records the opening date. operator
Deplete Goes to depleted, records the date and sets the remaining quantity to zero. operator
Move Opens the location tree; from-where and to-where are recorded. operator
Adjust qty Corrects the remaining quantity. Requires a written reason, which goes into the history. operator
Edit Location, unit, serial, batch, notes and custom fields. operator
Delete Soft delete: disappears from the lists, the history stays. manager

The statuses that aren't open or deplete

Open and Deplete only appear when they make sense. For every other status the Type allows there is the Set status dropdown: it is how you take a printer from in_service to maintenance, or a document from active to archived. Only that Type's valid statuses are ever offered.

Why status can't be edited by hand

On purpose. Status changes only go through the action buttons, and each one validates that the destination status is one the Type allows. That's why you can't “reopen” a depleted item: it will tell you “cannot go from depleted to open”. Quantity is an estimate; the fact that you opened it or finished it is a fact, and facts get recorded.

Prices are frozen

If you enter an item with a price, that price is locked forever and the field is disabled when editing. Price changes are never retroactive: what you paid for that spool last month is still what you paid. If you left it blank, you can fill it in later.

Internally, prices are whole numbers of cents, never decimals, to keep rounding errors out.

The Home screen

Home speaks in Concepts, not items. It answers three questions: what do I have, is anything running low, and let me act fast.

The strip along the top

Four numbers: active concepts, active items, open items, and how many concepts are below their minimum. The last one turns red if any concept is at zero.

The tree on the left is a filter

Click a zone and everything — the numbers on top, each card's stock and its item list — narrows to that branch and everything under it. A chip appears with the active code; click it to clear. This is how you do a physical stock-take of one cabinet.

Concept cards

  • Name, identifier, and the stock large in mono type, with the minimum beside it if you set one.
  • Left edge amber when low, red when at zero — and in that case the card opens itself.
  • Opening it shows the hierarchy: grouped by Variant, and under each variant, the items with their identifier, status, location and quantity.
  • If an item has a date field that looks like an expiry and fewer than 90 days remain, you get a exp 34d badge.
  • To the right of each item, the button that makes sense now: Open if it's in stock, Deplete if it's open.
Undo

After every quick action a toast appears bottom-right with an Undo button. It returns the item to its previous status — and that return is recorded in the history too, because history is never edited, only appended to.

Items with no concept

An item created without a variant belongs to no concept, so it cannot appear on any card. Those are grouped at the bottom in a Standalone items card, which only shows up when there are some.

Depleted items are hidden by default; there's a Show depleted checkbox at the top right.

The layout: a grid, and a tree you can drag

The cards are laid out as a grid that refills itself: on a wide monitor you get three or four columns, on a laptop two, on a phone one. Nothing is configured — the browser fits as many columns as the window allows and rearranges them as you resize it.

The location tree has a drag handle on its right edge. Pull it to whatever width your location names need and it stays there, on this computer, from now on. Double-click the handle to put it back; with the keyboard, focus it and use the arrow keys.

An open card scrolls inside itself once it gets past about ten items, so one very full concept can't stretch its whole row of the grid.

Searching your items

The Items page is the full listing, with a filter bar whose filters combine with each other:

  • Statuses: pills you switch on and off. By default in stock and open are on; to see everything, switch them all on.
  • Type and Concept: dropdowns.
  • Location: always includes sub-locations.
  • Free text: searches the identifier, serial number, batch number and notes.

The table shows identifier, type, concept, status, location, remaining, received date and price. Any row opens the detail drawer.

The full add form

The Add item button opens the long form, for when you want full control. The clever bit is the first field: picking the Type rebuilds the form and the fields you defined for that type appear. You can also pick a Variant (and then it inherits unit and pack size), or leave it blank to create a standalone item with no catalogue behind it.

Filters you can type into

The type, concept and variant filters are search boxes, not just dropdowns: start typing and the list narrows as you go. It ignores accents and capitals, so hepta finds Heptà, and the arrow keys plus Enter pick without touching the mouse.

They also narrow each other. Choose a concept and the variant list only offers that concept's products; change the type and the variant filter clears itself, because a variant belongs to exactly one type and leaving the old one would show you an empty table for no visible reason.

Sorting by a column

Click any heading to sort by it, click again to reverse, and a third time to go back to the table's own order (newest first). The arrow in the heading tells you which way it is.

  • Names and places sort alphabetically, in the language you are reading — a Catalan reader gets Catalan order, not whatever language happens to be first in the record.
  • Quantities, dates and prices sort as numbers and dates, smallest or oldest first.
  • Rows with nothing in that column always sink to the bottom, whichever direction you sort.

Sorting happens on the server, over every item that matches your filters — not just the page in front of you. "The cheapest isopropyl alcohol we have" is one click, wherever it is in the list.

The three upper levels

These three pages are the catalogue. If you only ever use Quick Add, you may never open them.

Concepts

A table with the calculated stock, the minimum, how many analogous groups it has and a coloured dot for its state. You edit the name (multilingual), the functional unit, the minimum-stock threshold and notes.

Analogous

An Analogous group is a set of things that serve you interchangeably. Its reason to exist appears when one Concept has more than one: “Sanding discs” with one group per size, or “PLA filament” with one per diameter. Within a group you swap brands without thinking; across groups, you don't.

Variants

A Variant is one concrete commercial product: the thing you actually buy. This is where brand, supplier, catalogue reference, format, pack size and unit, purity and concentration live.

Moving things around the tree

You can reassign an Analogous group to a different Concept, or a Variant to a different Analogous group. When you do, the form warns you first:

Re-link warning

This will re-link 2 variant(s) and 7 item(s) to the new concept.

And when you save, updating all the descendants happens in a single transaction: either everything moves, or nothing does. You never end up with items pointing one way and their product pointing another.

History

Everything that happens leaves a trace, and the trace is written inside the same transaction as the change: if the change is saved, so is the record; if it fails, neither is.

These actions are recorded:

  • created, updated (one entry per changed field, with the before and after values)
  • status_changed, moved, quantity_adjusted
  • soft_deleted, restored

On the History page you can filter by entity type, by action, by user (if you are an administrator) and by identifier. Each row says who did it and when.

On top of that, every item's detail drawer has its own history tab, which is the same information filtered to that item: useful for answering “and this spool — where did it come from and who's touched it?”.

Append-only

History entries are never edited or deleted, not even when you delete the entity they refer to.

Users and permissions

There are four roles, cumulative: each can do everything the previous one can, plus a little more.

RoleCan
viewer Sees absolutely everything. Changes nothing.
operator + create items, open, deplete, move, adjust quantities, edit items.
manager + create and edit Concepts, Analogous groups, Variants and Locations; delete items.
admin + Types and Users.

The philosophy is everything visible, not everything editable: even a viewer can open every data page; they simply don't get the buttons. And that isn't only cosmetic — the server re-checks the permission on every request, so hiding the button isn't the security, it's just good manners.

Creating accounts

Since public registration closes after the first account, the rest are created by the administrator from Users → New user: name, username, optional email, temporary password and role. The role can be changed afterwards from the dropdown in the table, with one exception: you can't change your own role, because that would be the easiest way to lock yourself out of the admin area.

Passwords

The key icon next to your name in the sidebar opens Change password. You have to type the current one, and saving signs out your other devices but not this one.

If somebody has lost theirs, an administrator resets it from Users → the Password button on their row. No need to know the old one; that person is signed out everywhere and must use the new password.

You can also do it from the terminal:

cd packages/api
npx tsx --env-file-if-exists=.env scripts/create-user.mts \
  theirusername "their-password" "Their Name" operator

Language and colours

Three languages, two layers

At the bottom of the sidebar there's EN / DE / CA. It switches the interface text instantly and is remembered.

But there's a second layer: your own data names are multilingual too. Every name field (concepts, analogous groups, variants, locations, types, custom-field labels) has the three tabs. English is required and acts as the fallback: if you view the app in German and something has no German name, you see the English instead of a blank.

The colours

The palette icon, next to the languages, opens the picker. The whole look of the app comes from three colours:

  • Primary — buttons, links, active navigation and the overall tone of the backgrounds.
  • Secondary — accents and chips.
  • Accent — warm details.

The dark surfaces are tinted with the primary, so changing it doesn't just change your buttons: it transforms the whole app. There are four ready-made palettes and a button to go back to the original. The text on buttons is recalculated automatically so it stays readable whether you pick a light colour or a dark one.

The status colours — red for out of stock, amber for warning, green for fine — never change. A warning has to look like a warning even if you go for a pink theme.

Worth knowing

Both the language and the colours are stored in the browser, not in your account. Sign in from another computer and you're back to the defaults.

The workshop's logo

An admin can put the workshop's own logo in the same dialog. Pick an image — PNG, JPEG, WebP or SVG — and it appears in the sidebar, on the sign-in screen and on the public stock board. Large images are shrunk automatically before they are stored; an SVG is left alone, because it already scales.

The logo goes inside the database file, not in a folder beside it. That is deliberate: a backup of this product is one file, and a logo living somewhere else would be the first thing to go missing when somebody copies the database to a stick.

Colours read out of the logo

As soon as an image is loaded, the app reads the colours out of it and offers three schemes — Calm, Bright and Deep. They are the same colours from your logo, lit three different ways; hover one to see the whole app in it, click to keep it.

What it takes from the image is the hue — the thing people recognise as "our colour" — and then adjusts how strong and how bright it is, because the app's surfaces are dark and a brand navy taken raw would disappear into the background. Grey, black, white and transparent pixels are ignored: they are the paper, not the mark.

The workshop's, or just yours

The dialog has two halves and they answer different questions.

  • Save for the whole workshop (admins only) stores the logo, the name and the colours in the database. Every computer in the building picks them up, including ones nobody will ever open this dialog on.
  • Only on this computer is the old behaviour: your own three colours, kept in this browser, and they win over the workshop's. The reset button goes back to the workshop's look rather than to the factory one.

Deleting and restoring

Nothing you delete from the interface is actually removed. The row is marked with a deletion timestamp and every query skips it. Which means a deletion by mistake is not a loss of data.

The Bin

In the sidebar, for managers and admins, there is a Bin: everything that has ever been deleted, of any kind, with the date and a Restore button. Everything means everything — items, concepts and locations, but also requests, lots, suppliers, activities and pools.

Deleting for good

Sometimes you want the row gone: a supplier you invented by typo, a duplicated type, a test lot. In the Bin, managers and admins have Delete permanently, which asks you to type the human id before it does anything.

This one really is final

There is no undo, and the app refuses if anything still points at the row — it will tell you what. What survives is the History: the record that the thing existed, and that somebody destroyed it, is never removed.

The one rule is that parents come back before children. A variant cannot return into an analogous group that is itself still deleted, and the list tells you before you try: instead of the button you see “restore its analogous first”. Work top-down and everything lands back where it was, with the stock recalculated automatically.

Cascade delete

If you delete something with things hanging off it, the app doesn't just refuse: it shows you exactly what is in the way and offers to take it all down at once.

Example

Deleting it will also delete: 1 × Analogous · 2 × Variants · 3 × Items

The cascade happens in a single transaction and all of it lands in the Bin, restorable in order. The one deliberate exception is locations: deleting a shelf never deletes what is standing on it. A location cascade only takes empty sub-locations; if there are items, move them first.

Backups

The entire database is a single file. That's the great convenience of this design: making a backup means copying a file.

  • In development: packages/api/data/inventory.db
  • Under Docker: inventory-data/inventory.db inside the volume

Next to it you'll find inventory.db-wal and inventory.db-shm. Those are SQLite's working files. The safest approach is to stop the server before copying; that folds pending changes into the main file and copying inventory.db is enough. If you copy while it's running, take all three.

Restoring is the same in reverse: stop, replace the file, start again.

The API

Everything the interface does, it does by calling an ordinary REST API — and that API documents itself. Open /api/docs — http://localhost:3001/api/docs in development, or :3000 under Docker — and you get the complete list of operations with their parameters, and you can try them right there.

It's good for three things: automating bulk loads (entering a hundred items from a spreadsheet, say), connecting another tool, or handing the project to someone who has to carry it on. Errors always have the same shape: 

{ "error": { "code": "concept_in_use",
             "message": "Cannot delete: 1 analogous group(s)…" } }

Bulk in and out

Two tools on the Items page, for when doing things one at a time makes no sense.

CSV export and import

Export downloads every item as a CSV with status, location, quantities, price and custom fields. It opens in Excel, LibreOffice or whatever you use.

Import (manager role) goes the other way, in two beats: when you pick the file, the server reads it without writing anything and tells you how many rows it understood and which would fail and why. Only when you press Import is anything written, and it is written all or nothing: a spreadsheet with one bad row imports none of itself.

The trick

Export first even when you have nothing, to see the exact columns expected. The minimum is type, plus variant if you want it linked into the catalogue. Locations are given by their code (L01R01Z02).

QR code labels

Every row in the items table has a checkbox. Tick a few and a bar appears with Print labels.

Each label carries the identifier, the name, the location and a QR code pointing at that item inside your app. Scanning it with a phone camera opens its page: it is how you know what is in a box without opening it. When printing, the whole interface disappears and only the label sheet reaches the paper, in black and white, with no label split across pages.

How closely to track each thing

Not everything in the workshop deserves the same attention. So every Concept carries its own tracking level, and one workshop happily runs all three at once.

Level 1 — manual

You record opens and depletions, and that is all. You set your own threshold (tell me when 5 boxes are left). This is a complete way to use the app, not a stepping stone to something else.

Level 2 — estimated rate

You type what you think you use per month. It exists so that on day one, with no history at all, the app can answer how long will what I have last.

Once there are real depletions, measurement takes over — but your estimate is never erased. It stays beside the measured one:

You said 800/month. Measured: 500/month (3 boxes depleted over 2 months). Using 500.

That moment is deliberate. Seeing your own estimate corrected by reality is what makes the number believable.

Level 3 — activities consume it

You declare what each activity consumes and, when you record it, the app takes that much out of the open container. explains it.

The rule that never bends

An activity moves the quantity. Only a person declares a container finished. The app will tell you a bottle ought to be empty; it will never say so on your behalf — because the difference between what the recipe predicted and what the bottle really held is the most valuable number the app produces.

This changed in August 2026

Earlier versions of this manual said no estimate ever moves stock. That was wrong, and wrong in a way that made you do the work twice. Recording “I ran seven pH tests” is not a guess: it is a person saying what happened. The guess is the recipe — 5 mL a test — and the app keeps the two apart, which is precisely what the reconciliation in measures.

Requests

A request is “we need wood glue”. Nothing more. There is no purchasing decision inside it: the person who needs wood glue should not have to know which brand, which is why a request is made against the Concept.

Where it is born

The best place to ask for something is not the Requests page: it is the second you realise it has run out, with the empty bottle in your hand. So when you deplete the last item of a concept, the app opens the request form for you, with the concept already filled in.

You can also ask from Requests → Request something, or from the Forecast with one button for a whole list.

What you fill in

  • What and how much. Required.
  • Urgency: normal or blocking. Two levels on purpose — with five, everything is urgent within a month.
  • A note, if you want to tell the buyer something.

If somebody already asked

When you pick the concept, if an open request already exists the app says so and offers Add me too instead of writing a second row.

Why

Three identical requests are not information; one request with three people behind it is. It tells you the intensity of the demand, not just that it exists.

What happens next

The request moves from Open to In a lot, Ordered and Arrived, and whoever made it sees that in their own list without having to ask anyone. With no mail server, this is the feedback loop.

Choosing what to actually order

When you turn requests into a line, the form opens on the answer it can already work out:

  • If the person who asked named a preferred product, that one is selected and marked as their suggestion. Their note was already in the request; there is no reason to make you ask them again.
  • Otherwise the one you bought last time is selected, at last time's price.
  • Products already bought are listed first; ones that merely exist are grouped under Never ordered, so "the usual" and "we have this on file" are never confused.

Naming a product on the spot

A concept nobody has ever ordered has no products under it at all — and that is exactly the concept somebody has just asked for. New product lets you name it here: what the supplier calls it, the brand, the pack size. It is created as a real variant under that concept, so next time it is one click, and the price you type today becomes the "last time" price of tomorrow.

The quantity, and when it can't be worked out

Picking a product proposes a quantity: the amount requested, divided by the pack size, rounded up. The arithmetic is shown, not hidden — "you need 500 mL, the pack is 1 L, so 1".

Different units

If the request is in mL and the pack is in L, the app will not do that division. It says so and leaves the quantity alone, because dividing 500 by 1 and ordering five hundred bottles is a much worse answer than asking you to look.

Lots: buying and receiving

Where the two halves meet

A request names a concept — "wood glue, 500 mL" — because the person who needs it should not have to know which brand. An order names a product, because that is what a supplier can actually send. The lot line is where somebody crosses that gap, and the form is built so it is crossed once and remembered.

A lot is one order to one supplier. It happens in three stages: build it, order it, receive it.

Building it

Lots → New lot, pick the supplier, then add lines. Each line is the step from Concept to Variant: it arrives as “wood glue, 500 mL” and must leave as “1 × 1 L bottle of brand X, €41.80”.

The order reference comes later

You are not asked for it here, because it does not exist yet: the shop gives it to you after you place the order. It is asked for at the mark as ordered step, where you actually have it.

Suppliers are remembered. Start typing and the app offers the ones you already use, with how many lots and what you last paid. Typing a name that only differs in capitals does not create a second shop — SensLab and SensLAb are one supplier with one price history.

Pulling in what people asked for

A draft lot shows the open requests, grouped by concept and with the people behind each one. Tick the ones this order covers and they become lines, already carrying the quantity that was asked for.

That is the whole point of requests: somebody asked, you are buying, and neither of you had to send an email. Whatever you leave unticked stays open for the next order.

The screen makes that nearly automatic, because most reorders are repeats: it shows what you bought before with its price and date, and one click fills in both variant and price. If the pack size does not match what you need, it shows the maths — you need 500 mL · the pack is 1 L · quantity 1 — so the rounding is visible instead of silent.

Price at the moment of the decision

If the price you enter differs from what you last paid, the line says so right there: +12% since last order. The information where the decision is made, not in a report nobody opens.

Ordering it

Mark as ordered closes the lot to edits and moves all its requests to Ordered. From here the app counts the days until it arrives.

Receiving it — the part that pays for everything

The box arrives, you open the lot and say how many of each line came. On confirm, the app creates the items for you: humanId, price, location, expiry. Twelve bottles without typing twelve items.

  • Fewer arrived? That is normal. The line stays open for the rest, and there is a the rest will never come checkbox to close it when you give up.
  • They sent something else? Tick they sent something else and name what arrived. Items are created for the product that actually arrived, creating it if it is new.
  • Expiry: one per line, not twelve date fields.
What is never touched

A line has two sides: what you ordered and what arrived. The first is never overwritten. Editing 5 of A to say 4 of B would destroy exactly the interesting data.

What falls out by itself

With nothing to configure, the Lots page gradually tells you each supplier's behaviour: what share of lines they short-ship and how many days they take on average. That second number is precisely what the Forecast needs.

Forecast

The page is not a chart. It is a sentence and a button:

6 things will run out before you can reorder them.   [ Request all ]

Tick the ones you want or take the lot, and they become requests. That closes the cycle back on itself.

Where the numbers come from

  • Consumption is measured from real depletions, not from activities. So the forecast works even if nobody ever records an activity, and gets better if they do.
  • Lead time is learned from your own orders: the days between ordering a lot and receiving it. With no history yet it assumes 14 days and says so.

Honesty

With three depletions in three months nothing can be forecast, and the app says not enough history yet rather than inventing a figure. When it does have enough, it shows its working:

4 bottles in 90 days · 2 left · about 45 days

Activities and real cost

An activity is something you do that uses material: an analysis, a print run, a preparation. You declare what it consumes — panel prep → 3 tubes, 10 tips — and after that you only have to say how many times you did it.

Recording it

Three taps: which activity, how many times, save. If it cost more than writing it in the workshop notebook, nobody would do it.

Recording takes the material out of the open container of every concept in the map. Not a note beside the stock — the stock itself. If a concept has nothing open, the app tells you instead of staying quiet: the consumption has nowhere to land.

Which container? The oldest one that is open and still has something in it. A container reading zero is passed over whenever another open one can take the charge, so a bottle somebody forgot to close does not swallow a month of consumption while another open one stands beside it.

When the empty one is the only one open

It still takes the charge — the app cannot open the next bottle for you — but not quietly: it says the map thinks this is empty every single time, until you confirm it. Stock stops at zero, the overdraw keeps counting underneath, and the difference is recorded the moment you close it.

Two numbers per container

Each open container carries two figures, and keeping them apart is what makes the rest work:

FigureWhat it isFloor
Remaining What the app believes is in the bottle. This is what stock counts. Never goes below zero
Charged Everything the recipes ever took out of it. Keeps counting past empty

When the map says it should be empty

When the charged figure reaches what the container held, the app raises its hand: the map says supplyAA002 should be empty — is it? It never depletes anything by itself. You decide, with the bottle in your hand.

And it does not stop counting while you decide. If you keep working and the recipes charge past empty, that is not an error to be argued with — it is the bottle lasting less than the recipe said. The moment you mark it finished, the app writes down the gap, with its sign:

Recipes said 500 mL · the bottle held 500 mL · closed after 540 → 40 mL short
Recipes said 500 mL · closed with 60 left → 60 mL over
Why nobody is asked for a number

Because you do not know it. Nobody measures the last centimetre of a bottle before binning it. What you do know is it is empty now, and that single click is enough for the app to work out the rest.

Unassigned consumption

This is where it stops being an ordinary inventory. Picture a box of 400 tips, a map that says 10 per analysis, and 30 analyses recorded: the activities account for 300, but the box is empty. The remaining 100 are unassigned consumption.

Why we do not call it “waste”

Because it does not claim they were lost: only that no activity claimed them. Frequently it means a map is missing, which is useful information rather than blame.

The remainder is also counted per day the container was open. A box open for 40 days that lost 100 tips beyond its recipes was losing two and a half a day to hands that recorded nothing. That rate is shown beside the forecast as a measured burn rate.

What it does not do

It does not drive “days of stock left”. That number comes from real depletions — bottles actually finished — because the forecast has to work for a workshop that never records a single activity . The burn rate sits next to it as a second opinion, and it is what turns theoretical cost into real cost below.

Why per day and not per activity

Because splitting it between the activities assumes they caused it, which is the one thing you know they did not: they already declared what they took. A rate per day open assumes only that time passed, which is true.

For cost, the same remainder is attributed to the activities that use that concept, weighted by how much each one uses — because a cost has to land on something. From that come two costs per activity, always shown together:

  • Theoretical — the map times the price.
  • Real — theoretical plus its share of the unassigned.

The ratio between them (runs at 1.33× theoretical) is a real measure of how the process is going. Over months it is worth more than the inventory itself.

Changing a map

If you change a map, the app does not rewrite the past: it closes the version in force and opens a new dated one. March keeps being costed with March's recipe. Map history shows every version — which incidentally documents when your procedures changed, written by nobody.

Reusables and the recount

Mixing cups, paint pots and trays are neither consumables nor equipment: they are lent out and come back. The only thing truly consumed is what breaks.

So they are not items. A mixing cup carries no number and nobody will ever track one individually. What you need to know is how many are clean and how many you lose a month, and neither question requires individual identity.

Two granularities

  • Counted only — the cups. You know how many are available, in use and dirty. Never which one.
  • Identified — the trays, which carry a number. Each has its own state and location.

The recount is the measuring instrument

Nobody will ever record “I dropped a cup”. So the number always drifts upward. The correction is to open the drawer and count:

The app expected 260 · you counted 248 → 12 lost since the last count

That difference is your breakage, measured. Two recounts give you a monthly rate, and it is the only thing a reusable contributes to purchasing: you buy them at the rate you break them, without anyone ever reporting a breakage.

Filling the pool from the cupboard

The cups in rotation are not the only ones you own. There is also the box of 250 in the cupboard, unopened — and that box is an ordinary item. You buy it, receive it in a lot, and it shows up in the forecast like anything else.

When the rotation runs thin, open the pool and use Into rotation: say how many, and the app takes them out of the box and puts them into the pool.

60 into rotation · 440 left in the cupboard

That is what closes the circle. Cups break, the pool drops, the cupboard refills it, the cupboard runs low, and purchasing sees it — without the pool needing any idea of what buying is.

Where a kit is

If a tray has numbered slots you can put kits in it. And here is an important decision: a kit has no location of its own. Its position is the tray's. Move the tray and forty kits follow with nothing updated, and it can never happen that the tray is on the shelf while the kits think they are in the workshop.

The log bridge

If your workshop has a system that already knows what is happening (a machine controller, say) and writes a line-by-line record, the app can read it and turn it into inventory movements.

The channel is one-way: the machine controller says what happened, the inventory decides what it means. The inventory never answers back.

1. The line shape — configured once

Log bridge → Connect a log. You paste one real line and say what each part is: 

12:40:32  Mostra_DMK3-21099-2621703602  RegistreFeinaK
   time          object and identifier            event

The app derives the pattern and shows it applied to whatever lines you pasted. You never write a regular expression. Once done, this is never touched again.

2. The event dictionary — the living configuration

Here you say what each name does. RegistreFeinaK → take one cup from the pool. Since you author the names yourself, there will be thirty or forty in the whole workshop.

Quantities live here, never in the log

An event that takes three cups is a different event with its own name, not a number inside the line. That is what lets you, the day you find a map was wrong, correct it and re-read the entire history. Had the quantity been written into the lines, the past would be frozen with the error in it forever.

For the same reason, changing the effects opens a new dated version: replaying the past applies the recipe that was in force on the day.

3. Shadow mode

Every rule is born in shadow: it records what it would do without doing it. You review, then enable. The source has its own switch too: if either gate is shut, nothing is applied.

4. Unexplained events

Names the log used that nothing explains yet are not an error list: they are the screen where you build the rules. You see one that appears 200 times, you say what it does from right there, and it never appears again.

Things worth knowing

  • Each line takes effect exactly once. Re-read the same file as often as you like without fear.
  • You can replay old logs. Point the app at last year's record and get real consumption history from day one.
  • Unknown objects are treated differently: a tray that does not exist gets parked and queried — auto-creating assets is how you end up with 400 phantom trays from one typo. A new kit, by contrast, is always created.
  • Silence warns. If the log stops writing, nothing breaks: the numbers just quietly stop being true. So the app tells you when no line has arrived for too long.
What the log is really for

Not for “counting consumption”: stock still moves only when a person says a container is empty. What it does is turn the theoretical figure from whatever somebody remembered to record into something nearly exact — and once the theoretical is exact, what is left over is no longer “the part we failed to log”, it is genuine loss.

Instruments: manuals, spares and maintenance

A caliper is an item like a bottle of wood glue is an item. But it is the only kind of thing that other items belong with, and the only kind whose upkeep runs on a schedule. Both live in the Equipment tab of any item's panel.

There is no “instrument” feature

Neither of these is reserved for a type called instrument. A cupboard has a service interval; a torque wrench has a calibration certificate; a printer has a spare nozzle. Which things a workshop hangs off a machine is not knowable in advance, so the tab is on everything and you use it where it makes sense.

Attaching things

Attach, say what it is, find the item. Four relations:

  • Document — the instruction sheet, the manual, the calibration certificate.
  • Spare — the torch, the lamp, the column in the drawer.
  • Accessory — the weight set, the sampler.
  • Consumable — what it eats while it runs.

The link reads from both ends. The caliper lists its instruction sheet; open the instruction sheet and it tells you which caliper it describes. That matters because the instruction sheet is filed in the assembly area and the caliper is on a bench — and whichever one you have in front of you is the one you started from.

Maintenance plans

A plan is what has to be done and how often. How often can be counted two ways, and you can use either or both:

Counted inSuitsExample
Days Things that age on the calendar External calibration, every 365 days
Uses Things that age by working Internal check, every 500 runs
With both, whichever comes first

Every 6 months or 500 jobs means the plan falls due the moment either counter runs out. A plan that could only count one of the two would be wrong for half the equipment in any workshop.

Fill in last done when you create the plan. If you leave it empty the clock starts today, which quietly hides a machine that has already been out of calibration for a year.

Counting uses

+1 use counts one run against every plan on that item that measures uses. It is deliberately blunt: if your machine controller already knows how many jobs the machine did, the number should come from there, and the app has an entry point for exactly that.

Marking it done

Done writes the service into a record that is only ever added to, and starts both counters again — the days and the uses — because the service covered whatever was due. The record keeps the use counter as it stood at the time, so “serviced at 480 runs” stays meaningful years later.

Service history on the plan shows every one of them, with who and when and whatever note you left (the certificate number is the one worth typing).

On the Home screen

Anything overdue, or due within a fortnight, appears in a band above your stock, overdue first. Click a row and you are in that machine's panel.

It sits above the stock on purpose: a machine out of calibration stops work in a way a low bottle does not. When nothing is due, the band is not there at all.

Shared computers sign themselves out

A computer nobody has claimed signs you out after twenty minutes without a keystroke or a click, with a one-minute warning first. This is not about theft; it is about the record. A browser left signed in makes every depletion and every adjustment look like the work of whoever walked away last, and the history is the one thing here that has to be trustworthy.

Claiming your own computer

The monitor icon beside your name opens Remember this computer. Confirm with your password and this browser stays signed in as you — through shutdown, hibernation, suspend and closing the browser. It never times out.

  • The claim belongs to one person. A colleague who presses their own chord on your desk gets an ordinary session that times out, and yours comes back the next time you sign in.
  • It costs a password on purpose: without that, a bench machine left unlocked for two minutes would be enough for somebody to make it permanently theirs.
  • Signing out by hand keeps the claim — it is closing the door, not moving out. Forget this computer ends it, and signs you out immediately so the change is true straight away.

Signing everyone out

Because a claimed computer never signs itself out, there has to be one lever that reaches all of them. On the Users page, Sign everyone out, everywhere ends every session in the building at once — claimed computers included, and the admin's own session with them. For a laptop that has gone missing or a password that was watched over a shoulder, it is the honest answer.

Looking without an account

Opening the address without signing in shows a read-only stock board: concept names, quantities, what is low or empty, and the location tree. Nothing else — no item rows, so no serial numbers, no batch numbers, no prices, no notes and no names of people. Clicking anything asks you to sign in.

Decide this on purpose

That board is visible to anybody who can reach the server, which on a workshop network means everyone in the building. It is meant as a noticeboard — "is there any wood glue left?" answered without borrowing an account. If your stock list is not something you want on a noticeboard, keep the server off the shared network.

Browsing by place

The location tree is how you describe where things live. It is also how you look around: pick a place and the panel beside it lists what is there.

This answers the question somebody standing in front of a cupboard actually has — what is in this cupboard? — which the tree on its own never could.

  • Include sub-locations — on, the room shows everything in every shelf under it; off, only what is filed on the room itself. The far-right column shows the exact shelf whenever the list spans more than one.
  • Type and search narrow it further: supplies in the solvent cabinet.
  • Show depleted and inactive is off by default. A shelf full of empty bottles is not what the shelf holds.

Every row opens the full item panel, so a stock check is: pick the shelf, read down the list, open, deplete, move. No searching by name.

Signing in with a key chord

One computer, several people, and a handover every time somebody needs to record thirty seconds of work. Typing a name and a password for that is enough friction that the work gets recorded under whoever happened to be signed in already — which quietly ruins the one thing History exists for. So each person can have a key chord: about a second of typing that signs them in.

What a chord is

Two clusters of keys, each held down together for a moment. Press QWE and hold; let go; press UIL and hold. That's it — you're in. The order of keys within a cluster doesn't matter; the order of the two clusters does.

You don't choose your chord: the app generates it. That is not the app being precious. Two people cannot share a chord — the whole point is that it says who you are — and if everyone picked their own, half of them would collide and have to pick again. The app also picks keys that can actually be pressed: three keys of one hand, in neighbouring columns, never more than one row apart. That is why you get ZXD and never AYP. If you don't like the one you got, ask for another.

Getting one

The key-shaped icon next to your name in the sidebar opens Fast login key. There you can create one, ask for a different one, or throw it away. The keys are drawn as they sit on the keyboard, left to right, so what's on screen is the shape your hand makes.

You can practise it right there. While that panel is open the chord does nothing except tell you whether you got it right — otherwise learning your own gesture would sign you out every time you succeeded.

Under the chord there's a hold time slider, from a twitch to a deliberate press. It's stored on that computer rather than on your account, and deliberately so: at the sign-in screen the app doesn't know yet whose setting to apply. It belongs to that keyboard.

The same chord does all three things

  • Signed out → it signs you in.
  • Signed in as somebody else → it switches to you, and closes their session on that machine.
  • Signed in as you → it signs you out.

One gesture meaning make it me, which is why there is no second chord to remember for logging out. It works from any screen — the sign-in page, the public stock board, or the middle of the Items table while you are working.

Two screens read it even with the cursor in a text box: the sign-in form and the public board, because those are the two places somebody clicks into a field and then presses their chord. Everywhere else a text field swallows it, and it should: three letters at once, inside a search box, is just three letters.

Careful

A chord is an identification, not a password. Anyone who watches you press it can sign in as you, exactly like a code on a door. That is the trade you are making for the speed, and it is the right trade for a bench in a locked workshop and the wrong one for a machine strangers walk past. Your password keeps working either way, and an administrator can revoke anybody's chord from Users → Revoke. Wrong chords are rate limited, so guessing is not a practical way in.

Later

QR badges and NFC cards are the same idea with different hardware, and they are on the list. The chord came first because it needs nothing bought.

What it doesn't do yet

So you don't waste time looking for them, here is the honest list of what today's version is missing.

Behaviours worth knowing

  • A Type's key cannot be changed once saved. A custom field's key can: on save, values already stored on items are migrated to the new key in the same transaction.
  • Removing a field from a Type destroys nothing: the old data stays stored and simply stops being shown.
  • Prices are frozen when the item is created. That is deliberate.
  • Deleting a location never deletes the items standing on it.
  • Recording an activity does move stock — this is the one thing that changed since the first release. What never happens on its own is a container being declared finished.
  • Attaching a manual to a machine does not move it or change it. A link is a link; the item keeps its own location and status.

Doesn't exist yet

  • Native Excel export (the export is CSV, which Excel opens anyway) and importing anything other than items.
  • Password recovery by email: with no mail server, an administrator resets it.
  • Approval of requests before purchasing. Today the buyer sees everything asked for and decides; there is no sign-off step.
  • Automatic watching of the log file: you press read new lines or paste content. Everything already there is the hard part — reading on its own is what is left.
  • A log event that counts machine runs. The app can be told this machine did 40 jobs, but the log dictionary cannot be pointed at it yet, so today somebody presses +1 use.
  • A desktop application (Tauri).
