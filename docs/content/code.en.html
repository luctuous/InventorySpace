How to read this

There are two documents about this app and they answer different questions. The user manual says what it does. This one says how it is built and why it was built that way.

It is organised the way the code is: outward from the things everything else depends on. Shared types first, then the database, then the server, then the browser, then the desktop shell and the box it all ships in. Read it in order once, then use the contents rail.

Careful

This is the document that goes stale fastest, which is exactly why it was written last. When it disagrees with the code, the code is right. Every claim here is anchored to a path, so checking takes seconds — and the file comments are treated as part of the source, not as decoration, so the short version is usually at the top of the file itself.

The house style

Two habits recur everywhere and are worth naming up front, because they explain a lot of what looks unusual.

  • Comments say why, never what. If a comment could be deleted by reading the line under it, it should be. What survives is the reasoning that is not in the code: the case that was hit in production, the simpler version that turned out wrong.
  • One place per idea. Stock is computed in one file. Human ids are minted in one file. History is written in one file. The value is not tidiness — it is that changing the rule means changing one thing, and that a rule can be tested at all.

The map

One repository, npm workspaces, four packages. No pnpm, no turborepo, no nx: the person who ends up owning this should need exactly one tool they already have. 

packages/
  shared/    @inventory/shared    Zod schemas + types, imported by both sides
  api/       @inventory/api       Hono + Drizzle + SQLite, REST at /api/v1
  web/       @inventory/web       React + Vite + Tailwind

Why the shared package has no build step

@inventory/shared exports raw TypeScript. There is no dist/, no tsc -b, no watcher to forget to start. Vite compiles it as source; tsx does the same on the server. The cost is one line in packages/api/tsup.config.ts — noExternal: ['@inventory/shared'] — which inlines it into the production bundle. That is a good trade: one line of build config against a class of "why is my change not showing up" that would otherwise hit every day.

Why the levels are not folders

The domain has four levels — Concept, Analogous, Variant, Item — and it would be natural to give each one a folder holding its schema, route, service and page. The code does the opposite: it groups by mechanism (all routes together, all services together, all pages together), because the things that change together are the mechanisms, not the levels. A change to how pagination works touches every route; a change to Variants touches four files that are already named after it.

Convention

Anything in lib/ is infrastructure with no knowledge of the domain. Anything in services/ knows the domain and may touch the database, but never HTTP. Anything in routes/ knows HTTP and calls services. When a route starts doing arithmetic, it is in the wrong file.

If you change one thing

The rule most likely to be broken by accident is the second one. Summing quantityRemaining in a route is easy, looks harmless, and silently forks the definition of "in stock" — which is the number the whole product exists to produce. If you need stock, import it.

@inventory/shared — the contract

This package exists so that the server and the browser cannot disagree about what a Variant is. It holds no logic that touches a database and no component that touches a screen — only the shapes, and the pure functions that operate on them.

shared/src/constants.ts 178 lines

Every closed set in the product: item statuses, user roles, location levels, field kinds, tracking levels, pool states, log effects. All declared as const and turned into unions, so adding a status is one line and the compiler then lists every place that has to handle it. Also roleAtLeast(role, minimum), which is the single definition of "senior enough" used by both the API middleware and the navigation.

shared/src/schemas/common.ts ~120 lines

The pieces every other schema builds on: translatedTextSchema (a name in EN/DE/CA, English required), pagination, and money. parseMoneyInput("12,50") returns 1250 and accepts both decimal separators, because a German and a Catalan user type the same price differently and neither is wrong. resolveText(name, locale) falls back to English, then to the first non-empty value — a name is never rendered as undefined.

shared/src/schemas/type.ts ~150 lines

The most interesting file in the package, because it builds validators at runtime. buildCustomFieldsValidator(definitions) takes the field definitions a user invented in the Types screen and returns a Zod object that validates items of that Type. This is what makes user-defined fields real rather than a JSON blob nobody checks: a number field rejects text, a select rejects a value outside its options, and it does so on the server, where it counts.

shared/src/schemas/{concept,analogous,variant,item,location,history}.ts

One file per MVP-1 entity, each with the same three shapes: …Schema (what comes out), …CreateSchema and …UpdateSchema (what may go in). Create and update are separate types rather than one partial, because the fields you may set at creation and the fields you may change later genuinely differ — an item's price is locked once it exists.

shared/src/schemas/{request,lot,action,pool,forecast,log,equipment}.ts

The same pattern for everything after the first release. log.ts is the largest because the log bridge has the most vocabulary: sources, parsers, dictionary entries, effects, and the ingestion report.

shared/src/schemas/responses.ts 251 lines

Shapes that are not entities: quick-search results, the trash listing, users, passwords, and fast-login chords. It also holds usernameProblem(value) and the placeholder e-mail helpers, which the API and the browser both call so a username is judged by the same rule in both places.

The database

SQLite, one file, WAL mode, foreign keys on. Drizzle for the schema and the queries. The whole backup story is "copy the file", and every decision below is downstream of wanting to keep it that way.

api/src/db/schema.ts 708 lines

Thirty-odd tables, and the single most useful thing to read first. Conventions worth knowing before you scan it:

  • Every table gets auditColumns — createdAt, updatedAt, deletedAt. Timestamps are Unix integers in the database and ISO strings at the API boundary; the conversion happens in one place.
  • Money columns end in _cents and are integers. There is no float anywhere near a price.
  • Translated names are JSON columns typed as TranslatedText. Adding a fourth language needs no migration — that is the entire reason.
  • Denormalized parents are deliberate. A variant carries conceptId as well as analogousId, and an item carries both. It is redundant, it can drift, and it is worth it: the Items browser filters by concept without two joins. The drift is prevented by rule 6 — re-linking mass-updates descendants in one transaction.

api/src/db/client.ts 18 lines

Opens the database and sets two pragmas that SQLite does not set for you: foreign_keys = ON (off by default, which means a schema full of references that enforce nothing) and journal_mode = WAL (so a reader never blocks a writer). Both are per-connection, so this is the only place a connection may be made. It also creates the data directory, so a fresh install has nothing to prepare.

api/drizzle/*.sql 9 migrations

Generated by drizzle-kit and committed, because a migration that only exists on the developer's machine is not a migration. They are applied at boot by api/src/index.ts, which is what makes docker run on an empty volume work with no setup step. Reading their names is a decent history of the product: 0004_supplier_entity is the day suppliers stopped being a string, 0007_equipment is instruments, 0008_fast_keys is the key chord.

api/src/db/seed.ts 584 lines

Demo data, and it is designed rather than dumped. It deliberately includes a concept that is low on stock and one that is at zero, so the Home screen's warnings have something to warn about the moment you open it; an instrument and a document, so the non-consumable lifecycles are demonstrable at all; and a pool with a real history, so the recount means something. It refuses to run on a non-empty database.

api/src/db/reset.ts ~60 lines

Clears the 26 domain tables and keeps the auth tables. That exception is written in blood: deleting the database file to "start clean" locked the owner out of his own app twice, because the accounts went with it. Resetting the data should never cost you your login.

api/src/db/auth-schema.ts ~45 lines

better-auth's own four tables (user, session, account, verification), declared in Drizzle so they live in the same file and the same migrations as everything else. The role column is ours, added through better-auth's additionalFields with input: false so a client can never assign itself one.

The data model, drawn

Thirty tables is too many to hold in your head, but the shape is small. Everything hangs off one row type — items — and everything else is either a way of talking about items or a record of something that happened to them.

The spine

  types ──────┐                    locations ──┐   (self-parented tree)
  (user-defined│                     code, level │
   fields)     │                                 │
               ▼                                 ▼
  concepts ─→ analogous ─→ variants ─────→ items ←── the only physical thing
   "wood glue"   "1 L amber"  "Sigma 34873"   supplyAA042
      ▲            ▲             ▲            │  status · quantity_remaining
      └────────────┴─────────────┘            │  estimated_used · price_cents
        denormalised onto items and           │
        variants (concept_id, analogous_id)   │
                                              ├─→ item_links     (manual, spare)
                                              ├─→ maintenance_plans
                                              └─→ history        (append-only)

Read it downward. The three levels above items are descriptions of decreasing generality: what you need (wood glue), which products would do (1 L amber bottle), the exact product (Sigma 34873). Only the bottom row exists physically. Stock is computed from that row and nothing else, which is why the levels can be skipped entirely (Quick Add builds the whole chain behind you) without any number changing meaning.

The two dotted parents are the deliberate redundancy of: an item carries conceptId and analogousId as well as variantId. It can drift; it is kept honest by the mass-update transactions in routes/variants.ts.

What happens to them

requests ──(triage)──→ lot_lines ──(receive)──→ items   created automatically
   concept              variant                       humanId, price, expiry

actions ──(record)──→ charges the open item of each concept in its map
   ▲                        │
   │                        ├─→ quantity_remaining  clamped at 0 → stock
   └── log_lines            └─→ estimated_used      uncapped → the gap

pools ──(events)──→ pool_units          commissioned FROM an item
   "20 mL vials"      available/in_use/dirty        (cupboard → rotation)

These are the four operational loops of, and they meet at items too. Buying creates items; activities consume them; pools take them out of the cupboard and put them into rotation; the log does at scale what a person would do by hand. Nothing here is a separate inventory.

The one asymmetry worth remembering

A kit has no location of its own. You track the material it sits in — the tray, the vial — so moving a tray moves forty kits with zero rows updated. That is why occupancies exists and why kits are not items.

Who owns whom

Deleting follows ownership, with one exception that matters:

  • A concept owns its analogous groups, which own their variants, which own their items. Deleting upward cascades, with a preview first (, cascade.ts).
  • A location owns nothing. A shelf does not own the bottle standing on it, so deleting a place never deletes what was on it — it simply refuses while anything is there.
  • History owns nothing and is owned by nothing. It survives the purge of the row it describes, which is why it stores the human id.

Who you are

Authentication is better-auth on the same SQLite file. Four files make it behave the way a workshop needs rather than the way a SaaS needs.

api/src/auth.ts ~90 lines

The configuration, and three decisions inside it:

  • Registration closes after the first account. The databaseHooks.user.create.before hook makes the first user an admin and throws for everybody after. The Users admin page needs to create accounts through the same API, so it flips adminCreateBypass around its call — safe because Node runs the handler synchronously up to the await.
  • The username validator is replaced. better-auth allows only [a-zA-Z0-9_.], which rejects Müller. Ours is usernameProblem from the shared package, which forbids only what genuinely breaks.
  • trustedOrigins matters only in development, where the browser is on :5173 and the API on :3001. In production one port serves both, so every request is same-origin — including over the LAN by IP.

api/src/lib/secret.ts 38 lines

Generates the cookie-signing secret once and keeps it beside the database. This file exists because of a bug that only appeared in a real container: better-auth refuses the default secret when NODE_ENV=production, so the image built, started, printed a warning, and then died on its first authenticated request. Asking the user to set an environment variable would have been the easy fix and the wrong one — the promise is "download, run one command, open your browser". BETTER_AUTH_SECRET still wins when set.

api/src/middleware/auth.ts ~70 lines

requireRole('manager'), used as route middleware. It resolves the session from the cookie, puts the user on the context, and compares with roleAtLeast — the same function the sidebar uses to decide what to show, so the screen and the server can never disagree about what a manager may do. The screen is politeness; this is the enforcement.

api/src/lib/fast-login-plugin.ts ~110 lines

Signing in with a key chord, as a better-auth plugin rather than a route of our own. The reason is narrow and decisive: only better-auth can mint a valid session cookie, and forging one next door would be a second implementation of the one thing worth having exactly one of. The endpoint is POST /api/auth/sign-in/fast-key.

One chord means three things depending on who is already signed in — sign in, switch user, sign out — which is why there is no second chord to remember. Switching deletes the previous session rather than leaving it lying around on a shared machine. Attempts are throttled to twelve a minute, because the space is only about 4,700 chords.

api/src/services/fastkeys.ts ~150 lines

Generating a chord that a hand can actually make. The keys are not drawn from the alphabet but from the keyboard's geometry: one key per column, three adjacent columns of one hand, no two fingers more than one row apart. That single constraint is what rules out a y ñ and produces z x d. The two groups prefer opposite hands, because alternating is faster to press and easier to remember as a rhythm.

The chord is stored as written, not hashed, and that is a decision, not an oversight: signing in means finding the owner from the chord, which a salted hash cannot do, and the owner must be able to look it up again after a holiday. It is what it was always meant to be — an identification, not a password. Passwords stay hashed and keep working.

api/src/routes/public.ts ~200 lines

The only unauthenticated data in the product, and deliberately its own router rather than a relaxed requireRole on the real ones. It serves two things: the workshop's branding, which the sign-in screen needs before anybody has signed in, and one hand-written read-only view of stock for the signed-out Home.

What leaves this file is a fixed list — concept names, quantities, units, thresholds, the location tree. No item rows, so no serial numbers, no prices, no notes, no names of people. One endpoint rather than public variants of /concepts, /items/metrics and /locations, because four relaxed endpoints are four things to get wrong later and each takes filters this view is not meant to answer. Adding a field here is a decision to publish it to everyone on the network.

web/src/lib/device.ts ~90 lines

The "remember this computer" claim: a note in localStorage saying which account has adopted this browser. It is not a credential — the session cookie is what keeps you signed in — it records why that cookie was made a lasting one, and for whom.

Two things read it. Sign-in asks better-auth for rememberMe only when the person signing in is the claimant, which is why a colleague pressing their chord at your desk gets an ordinary session. And the idle timer stands down entirely. Clearing browser storage un-claims the machine, which is the right direction to fail in: you get the cautious behaviour, not the permissive one.

web/src/components/IdleTimer.tsx ~100 lines

Twenty minutes of silence ends a session on a shared computer. The problem it solves is attribution, not theft: a browser left signed in makes every depletion look like the work of whoever walked away last, and History is the one thing here that has to be trustworthy.

The check is against the clock, never against a countdown — timers do not run reliably while a laptop is suspended, so a decrementing counter would come back from a closed lid convinced no time had passed. The one-second interval only reads Date.now() and compares. Verified with Playwright's fake clock in scripts/verify-ui.mjs, because the real test takes twenty minutes.

The HTTP skeleton

api/src/index.ts ~45 lines

The entry point: apply migrations, then listen. It prints the LAN addresses as well as localhost, which is a small thing that saves a real conversation — the server is meant to be reached from every machine in the workshop, and guessing its address is the first thing that goes wrong.

api/src/app.ts ~140 lines

Assembles the routers, mounts better-auth at /api/auth/*, serves the OpenAPI spec and Swagger UI, and — when SERVE_WEB=1 — serves the built frontend with an SPA fallback so deep links work. That flag is what turns two dev servers into one production port, and it is the whole of the difference between the two layouts.

api/src/lib/router.ts ~30 lines

A thin wrapper over OpenAPIHono that fixes the default validation error into the app's uniform error shape. Every router is created through it, which is how "all I/O is validated" stays true without anybody remembering to do it.

api/src/lib/openapi.ts ~60 lines

Helpers so route definitions stay readable: jsonBody(schema), jsonContent(schema), errorResponse('Not found'). Without them every route carries fifteen lines of OpenAPI boilerplate and nobody reads the interesting part.

api/src/middleware/error.ts ~80 lines

One error shape for the entire API: { error: { code, message, details? } }. ApiError plus the named constructors notFoundError and conflictError. The details field is what makes a refusal useful rather than final — a blocked delete returns the cascade preview in it, and the browser turns that refusal into an offer ("this will also delete 2 variants, 3 items").

api/src/lib/serialize.ts ~50 lines

The boundary between database types and JSON: timestamps to ISO strings, cents to a decimal string, nulls preserved. It exists so that no route ever hand-rolls a date format, which is exactly how two endpoints end up disagreeing about what a date looks like.

api/src/lib/csv.ts ~120 lines

A hand-written RFC-4180 reader and writer — no dependency, because the format is a hundred lines and a dependency is forever. Import is a dry run first, then all-or-nothing in one transaction, so a bad row at line 400 cannot leave 399 rows imported.

A request, end to end

The fastest way into an unfamiliar codebase is to follow one thing all the way through. This is pressing “Deplete” on the Home screen — the smallest interesting action in the product, because it is the moment a human declares a container finished, and that declaration is the only thing the whole forecast trusts. 

1. HomePage.tsx          the button calls useDepleteItem()
2. api/entities.ts       useMutation → api('/items/<id>/deplete', { method: 'POST' })
3. api/client.ts         fetch, credentials: 'include', JSON headers
   · vite proxy            /api → :3001   (development only; one port in production)
4. app.ts                routes it to itemsRouter
5. middleware/auth.ts    requireRole('operator') → session from cookie → c.set('user')
6. lib/router.ts         validates the params against idParam
7. routes/items.ts       the handler — twelve lines, and it delegates
8.   └─ statusChange()   db.transaction(() => {
9.        getActiveItem      404 if it is gone
10.       assertValidStatus  the Type must allow 'depleted'
11.       requireCurrent     409 unless it was in_stock or open
12.       reconcileOnClose   the signed gap, written here and nowhere else
13.       db.update(items)   status='depleted', quantity_remaining=0
14.       logEvent()         same connection ⇒ same transaction
15.     })
16. lib/serialize.ts      timestamps → ISO, cents → decimal
17. api/entities.ts       onSuccess → invalidate ['items'] and ['history']
18. HomePage.tsx          stock re-renders; a toast offers Undo

Eighteen steps and two of them think. Everything from 1 to 6 is transport, and everything from 16 to 18 is transport back. The product lives in steps 8 to 14, inside one transaction, in one file.

What each layer is allowed to do

  • The page may not know that a status is a string. It calls a hook.
  • The hook may not know a URL is a URL. It calls api() and declares what to invalidate afterwards.
  • The route may not compute. Look at step 7: it reads the id, names the new status, and hands over. Twelve lines.
  • The transaction is where correctness lives — and note the order: every refusal (9, 10, 11) happens before the first write.

When it goes wrong

throw notFoundError('item', id)        →  middleware/error.ts
                                       →  { error: { code: 'not_found', … } }  404
                                       →  api/client.ts throws ApiRequestError
                                       →  the component catches it and says so

One shape, all the way out. That is what lets a component turn a refusal into an offer instead of a red box — the delete flow catches exactly this and reads details.cascade out of it.

The second trace worth doing yourself

Follow POST /api/v1/actions/record the same way, through services/actions.ts. It is the same skeleton with a harder middle: one activity fans out to several concepts, each one finds its open container, and the two figures per container part ways. If you understand that one, you understand the product.

The services — where the thinking is

If you read one directory, read this one. Routes are plumbing; the product's actual opinions live here.

api/src/services/ids.ts ~90 lines

Mints the human-readable ids: CON006, supplyAA042. A registry table holds the counter per prefix, and the increment happens inside the same transaction as the insert — so a failed insert cannot burn an id, and two simultaneous creates cannot get the same one. The lettered form rolls AA999 → AB001, which is tested, because it will happen once in three years and be baffling.

The rollover, which is three lines and will confuse somebody once every three years: 

if (!row) {
  letterPart = style === 'lettered' ? 'AA' : '';
  numberPart = 1;
} else {
  letterPart = row.letterPart;
  numberPart = row.numberPart + 1;
  if (style === 'lettered' && numberPart > 999) {
    letterPart = nextLetters(letterPart);   // AA999 → AB001
    numberPart = 1;
  }
}

api/src/services/history.ts ~80 lines

logEvent(event) — one row per mutation. It records the entity's human id alongside its uuid, so a purged row still reads as a sentence.

The interesting part is what it does not take: a transaction. It writes through the same global db handle as everything else, and it still rolls back with the mutation it records — because better-sqlite3 is synchronous and there is exactly one connection, opened in db/client.ts, and a SQLite transaction belongs to its connection. Calling it inside a db.transaction() callback is therefore enough.

Fragile

That is a real guarantee resting on an implicit condition. Introduce a connection pool, or make any of this asynchronous, and history would silently stop being part of the transaction would still be written down and no longer be true. If that ever changes, logEvent must take the transaction explicitly.

api/src/services/stock.ts 52 lines

The single definition of "how much do we have", and it is worth seeing in full because it is smaller than people expect. Nothing else in the codebase sums a quantity. 

const ACTIVE_STOCK_STATUSES: ItemStatus[] = ['in_stock', 'open'];

export function stockByConcept(locationIds?: string[]): Record<string, number> {
  const rows = db
    .select({ conceptId: items.conceptId, stock: sum(items.quantityRemaining) })
    .from(items)
    .where(
      and(
        inArray(items.status, ACTIVE_STOCK_STATUSES),
        isNull(items.deletedAt),
        isNotNull(items.conceptId),
        locationIds ? inArray(items.locationId, locationIds) : undefined,
      ),
    )
    .groupBy(items.conceptId)
    .all();
  …
}

Three things are decided in that one where. Only in_stock and open count. It sums quantityRemaining, not the original quantity, so a half-used bottle counts as half. And the optional locationIds — a subtree from subtreeIds() — is what makes the Home tree a filter rather than navigation: the same aggregation, one extra condition.

Corrected 2026-08-08

An earlier draft of this manual credited this file with two things it does not do. Excluding types with countsAsStock = false happens in routes/concepts.ts (the stockOnly filter) and in services/forecast.ts; deriving a pool's counts from pool_units happens in routes/pools.ts. Both were found by fetching the code to quote it, which is the argument for quoting code.

api/src/services/actions.ts 370 lines

Recording an activity, and the file where the product changed its mind. Rule once said estimates never move stock. That was wrong, and the reason it was wrong is worth keeping: it conflated the recipe ("a pH test uses 5 mL" — a forecast) with the act of recording one ("I ran a pH test" — a fact). Doing it by hand would have moved stock seven times, so recording it moves stock too.

What did not change is the other half: only a person declares a container finished. Two figures are kept per container — quantityRemaining, clamped at zero and summed into stock, and estimatedUsed, uncapped. Their difference when the container is closed is the signed gap between what the recipe claimed and what the bottle held, and that gap is the most valuable number the system produces.

openContainerFor(conceptId) lives here and is shared with the log bridge. It was rewritten after two defects that only appeared in real use: a container reading zero but still open absorbed every charge while a full bottle sat beside it, and a null-quantity container won for being oldest and swallowed consumption invisibly.

api/src/services/cascade.ts 253 lines

Works out what a delete would take with it, and does it in one transaction if you agree. The interesting rule is the exception: deleting a location never deletes the items on it. Everywhere else a parent owns its children; a shelf does not own the bottle standing on it, and a UI that quietly deleted your inventory because you tidied the location tree would be indefensible.

api/src/services/purchasing.ts 290 lines

Requests and lots. Receiving a lot line is the largest single labour saving in the product: it creates the items automatically — human ids, price, location, expiry — so twelve bottles arrive without typing twelve items.

A line has two sides and neither is ever overwritten. Ordered 5 × A, received 4 × B: editing the line to say "4 × B" would destroy exactly the interesting data. Items are created for the variant that actually arrived, and the discrepancy is kept — accumulated, those become "short-ships 8% of lines" and "11 days average", and that second number is what the forecast needs. The forecast gets better purely from using the purchase flow, with nothing to configure.

api/src/services/forecast.ts 245 lines

"What runs out before I can reorder it." Consumption is measured from real depletion events, not from recorded activities, and that is deliberate: the forecast works for a workshop that never records a single activity, and improves if they do. Lead time is learned per supplier from ordered-date to received-date.

Correction

An earlier version of this manual said the unassigned per-day burn rate feeds daysRemaining. It does not, and never did — see forecast.ts, where daysRemaining uses rate.monthlyRate only. The per-day figure is display, and feeds real cost.

api/src/services/logbridge.ts 503 lines

Reads the machine controller's line-by-line output. Four decisions carry it:

  • Quantities live in a dated dictionary, never in the log. The log says what happened; how much that costs is our business, and versioning it by date means history can be reprocessed when a map is corrected.
  • Unknown events are a configuration screen, not an error list. A new name appears, you say what it does, it never appears again — setup as a feedback loop instead of a blank page.
  • Unknown objects, asymmetrically. An unrecognised asset is parked and queried; auto-creating is how you get 400 phantom trays from one typo. An unrecognised kit is created silently — there will be thousands and they are transient.
  • Shadow mode before activation. A new rule records what it would do for a day; you review; you enable it.

Ingestion is idempotent — each line takes effect exactly once, checked by the suite re-reading the same file. The silence detector notices when no line has arrived for hours during working time, because a log that stops does not shout; the numbers just quietly stop being true.

api/src/services/maintenance.ts 176 lines

Plans count days, uses, or both, and due means whichever runs out first — which is what "every 6 months or 500 jobs" actually means. nextDueAt is recomputed on every change so "what is due" is one indexed query. Never-serviced starts the clock at the plan's creation: the only honest guess, and visibly wrong in a way somebody will correct.

The routes

Sixteen files, one pattern. Each declares its routes with createRoute (method, path, middleware, request schema, every response it can produce), then registers a handler. The schemas come from @inventory/shared, never inline, so the OpenAPI spec at /api/docs is generated from the same objects that do the validating and cannot drift from reality.

One route, in full, because the other hundred look like this: 

const listRoute = createRoute({
  method: 'get',
  path: '/concepts',
  tags: ['concepts'],
  middleware: [requireRole('viewer')] as const,
  request: {
    query: paginationQuerySchema.extend({
      search: z.string().optional(),
      /** Home passes this: instruments and documents are not stock. */
      stockOnly: z.enum(['true', 'false']).optional(),
    }),
  },
  responses: {
    200: {
      description: 'Paginated concepts with computed stock',
      ...jsonContent(listResponseSchema(conceptWithStockSchema)),
    },
    401: errorResponse('Not signed in'),
  },
});

Everything a caller needs is declared, not implied: the role, the query shape, and every response it can produce. The OpenAPI page at /api/docs is generated from this object — the same object that validates — so the documentation cannot drift from the behaviour. The handler underneath is usually five lines.

Note the comment on stockOnly. That one flag is where instruments and documents leave the Home screen, and the rule is subtler than it looks: a concept counts as stock if any of its live items is of a counting type — and a concept with no items at all is kept, because it has simply not been used yet and hiding it would make new concepts look broken.

And the mirror image on the other side. The query key is ['concepts', 'list', params], so a mutation invalidating ['concepts'] refreshes every variation of every list without naming any of them. 

export function useConcepts(params: ConceptListParams) {
  return useQuery({
    queryKey: ['concepts', 'list', params],
    queryFn: () =>
      api<{ data: ConceptWithStock[]; meta: PaginationMeta }>('/concepts', {
        query: { page: params.page ?? 1, search: params.search || undefined, … },
      }),
    placeholderData: keepPreviousData, // old page stays while the next loads
  });
}

Adding an endpoint

Schema in @inventory/shared → createRoute with every response listed → handler that calls a service → hook in web/src/api/. If the handler starts computing rather than delegating, the logic belongs in services/.

api/src/routes/items.ts — ordering ~40 lines

Sorting is a query parameter, so SQLite does the work over every matching row. Sorting the 25 rows already in the browser would be a lie: "the cheapest item" would mean "the cheapest of the 25 that arrived most recently". Each router declares its own key list, so an unknown key is a 400 at the edge rather than a silent fallback to an order nobody asked for.

Two details are load-bearing. Translated names are JSON columns, so they sort through json_extract in the reader's own language with an English fallback — the same rule resolveText() applies in the browser. And NULLs are forced last in both directions: SQLite sorts NULL first, so a page of items with no price would otherwise open with a column of dashes.

Talking to the API

One fetch wrapper. It sends cookies, sets the JSON headers, and — the useful part — turns the API's uniform error shape back into an ApiRequestError carrying code, message and details. Three colours

web/src/styles/index.css ~200 lines

The whole theme derives from three custom properties — primary, secondary, accent — through color-mix(in oklab, …). Surfaces, borders, muted text and tints are all mixes of the primary with the background, which is why changing one variable in devtools retints the entire application instead of half of it.

oklab rather than sRGB is the detail that makes it work: mixing in a perceptual space keeps a 14% tint looking like a 14% tint at every hue, where sRGB would make the violet muddy and the amber fluorescent. Status colours — red, amber, green — are deliberately not derived. "Low stock" must be the same red whatever somebody has chosen as their primary.

web/src/theme/ThemeProvider.tsx ~120 lines

Reads the three colours from localStorage and writes them onto documentElement. Defaults live in CSS, not here, so a first load has no flash of the wrong palette. It also carries the contrast helper: given a chosen primary it computes relative luminance and picks black or white for text on top, so somebody choosing a pale yellow gets readable buttons instead of a designer's assumption.

web/src/lib/palette.ts ~250 lines

Reading a theme out of a logo. Nobody wants to pick three hex values, and almost everybody already has a logo — which is a colour decision somebody made on purpose, so the honest shortcut is to read it back out.

Pixels are bucketed by hue, 24 buckets of 15°, rather than clustered properly: a logo has three or four flat colours, not a photograph's gradient, and k-means would be more code to read for an answer that is no better. Transparent, grey, near-black and near-white pixels are skipped — they are the paper, not the mark, and keeping them would give every logo in the world the same grey theme.

What survives from the image is the hue; saturation and lightness are re-set three ways (Calm, Bright, Deep). That is not a liberty — the app's surfaces are dark and tinted by the primary, so a brand navy taken raw would disappear into the background and a brand pastel would wash it out. A single-colour logo gets the other two hues by rotating around the wheel, which is a triad rather than an apology.

api/src/services/settings.ts ~35 lines

A key/value table rather than one row with a column per setting: every new setting would otherwise be a migration, and settings are exactly the thing that gets added on a Tuesday afternoon. The value is JSON, validated by a Zod schema at the route — the shape lives in the type system, not in the DDL.

The logo travels as a data: URI inside that JSON, capped at about 300 KB. It is in the database on purpose: a backup of this product is one file, and an uploads/ directory beside it would be the first thing to go missing. Stored JSON that no longer parses falls back to the built-in look rather than throwing — a bad logo must not be able to take the whole app down.

Two layers of language

Interface text and user data are translated by different mechanisms, and confusing them is the classic mistake.

web/src/i18n/index.tsx ~90 lines

t('items.title') over three JSON dictionaries, falling back to English and then to the key itself — so a missing translation shows items.title, which is ugly on purpose and gets fixed. It interpolates (t('lots.itemsCreated', { n: 6 })) while leaving unknown placeholders untouched, so pre-existing strings containing braces did not break the day interpolation was added.

web/src/i18n/{en,ca,de}.json 691 keys each

Adding a language is adding one file. There is no key in one that is missing from another — that is checked, not hoped for.

The second layer is data: a concept's name is a JSON column {"en": …, "de": …, "ca": …} rendered through resolveText(name, locale) from the shared package. That is why adding a fourth language needs no migration, and why MultilangInput.tsx exists — a three-tab field with English required.

Reading a key chord off the keyboard. Keys are identified by event.code — position, not character — which is what makes the same gesture work on a Catalan, German or English layout.

Two rules earn their keep. A group ends when the fingers lift, not when the timer fires: every new key restarts the hold clock, and the group is whatever is still down when the hand stops moving, so a slow hand is not read as two groups. And the detector stays quiet while you are typing — except where a field opts back in with data-chord-ok, which the sign-in form does, because that is exactly where the cursor lands by itself and a silently ignored chord there would break the one screen the feature exists for.

The desktop client

desktop/src-tauri/src/main.rs 220 lines

A window onto a server — not a second copy of the app. That is the design decision, and it is worth stating plainly because the opposite is the obvious choice: this product is one server holding one file that the whole workshop shares, so an installer carrying its own API and its own database would quietly give every bench a private inventory, which is precisely what the app exists to prevent.

What it buys over a browser tab is a window with no address bar to wander out of, no tab to close by accident, and a keyboard the operating system hands straight to it — which is what makes the key chord practical on a shared bench.

Three startup paths: no saved server opens the connect screen; a good one opens the app; a saved server that has since moved falls back to the connect screen showing what it tried, rather than a blank rectangle. It probes /api/v1/health from Rust rather than from the page, which sidesteps CORS entirely. normalize() accepts what a person actually types — workshop-pc:3000, 192.168.1.20:3000, with or without a scheme — and its unit tests caught a real bug on the first run: trimming trailing slashes before checking the scheme turned a bare http:// into http://http:, a perfectly valid URL for a host nobody has.

desktop/ui/index.html ~180 lines

The connect screen, and the only interface the desktop app owns. One static file with no bundler and no dependencies, calling window.__TAURI__ directly — everything else it shows comes from the server.

Dockerfile 52 lines

Multi-stage. The build stage installs a C toolchain because better-sqlite3 is a native module; the runtime stage copies only what is needed and runs node dist/index.js with SERVE_WEB=1, so one port serves the SPA, the API, the docs and the manuals.

The lesson from the first real run

NODE_ENV=production is set in exactly one place in this repository — here — and nothing else runs with it. Everything that behaves differently in production had therefore never been executed. The first docker run found it: the container started, printed a warning, and died on its first authenticated request (, lib/secret.ts).

Where the bodies are buried

The things that will bite you, collected in one place. Most were found by using the app rather than by reading it.

Traps in the code

  • Both ends of a move must move by the same amount. pools.ts once clamped the source at zero while crediting the destination in full, so an oversized take invented cups out of nothing — 692 of them from one click, in the very number the recount measures attrition against. Any transfer between two counters is suspect until you have checked both sides.
  • Derived columns can be right on screen and wrong in the database. An identified pool's counts are computed from its units on read, so a bulk event wrote nonsense into the stored columns and nobody could see it. If a value is derived on read, refuse to write it.
  • A default filter is a claim. The Items page defaulted to in_stock+open and said "Nothing here yet" — telling you your instrument did not exist. An empty state must distinguish "nothing" from "nothing matching".
  • Rendering the same thing twice breaks querySelector. The sidebar exists as a desktop column and a mobile drawer; anything looking for an element in it must pick the visible one.
  • `localhost` is a privileged origin, and this app never runs there in real life. Two blockers hid behind that for months: crypto.randomUUID() does not exist outside a secure context, so the first account could not be created from any other machine; and better-auth marks its cookie Secure in production, which a browser discards over plain HTTP, so nobody stayed signed in past a reload. Any browser-facing change wants one pass against http://<lan-ip>:3000.
  • History is inside the transaction by accident of architecture, not by argument. logEvent() takes no transaction and writes through the global handle; it rolls back with its mutation only because better-sqlite3 is synchronous and there is exactly one connection. A pool, or an async path, would silently break while leaving it written down.
  • The denormalized parent ids can drift. They are kept correct by mass-update transactions in variants.ts and analogous.ts. Writing a conceptId anywhere else is how they stop being true.

Version choices worth knowing

  • Zod v4, not v3 — @hono/zod-openapi requires it. The real rule (one version workspace-wide) holds.
  • React Router v8, not v7; TypeScript 7 (native tsgo).
  • items.createdBy is plain text, not a foreign key: deleting a user must never break an item.
  • Docker keeps the workspace layout instead of flattening.

Not built, on purpose

  • Automatic log watching. Everything else in the log bridge exists; ingestion is triggered by a button or a paste. The silence detector is already there to pair with a watcher.
  • A log effect that counts machine runs. POST /items/:id/uses exists; the dictionary entry kind that would let a machine controller line raise the counter does not.
  • Approval before purchasing. Held back because it depends on whether the workshop wants a sign-off step at all.
  • A desktop app carrying its own server. The client half is built; the sidecar needs a per-platform node and a per-platform better-sqlite3, and is a product decision rather than more of the same work.

Never tested against reality

The log bridge has never been connected to an actual machine controller. It works against pasted lines and against the source the suite creates, and the design was settled in detail — but the day it is pointed at a real instrument's output will be the first day, and the first day is always different.

If you are picking this up

Read db/schema.ts first, then services/stock.ts and services/actions.ts. Those four things are the product; everything else is how it reaches a screen.

A claimed computer never expires on its own

session.expiresIn is a year, and that is not laziness. How long a session lives is decided by the cookie: a shared machine gets a browser-session cookie plus a twenty-minute idle rule, a claimed one gets a lasting cookie and is meant to survive shutdowns. With a thirty-day server expiry the claimed machine would throw somebody out after a long holiday for a reason no user could ever explain. Ending a claimed session is therefore always deliberate: signing out, or POST /users/sessions/revoke-all.

A lot line may create the variant it orders

POST /lots/:id/lines takes either an orderedVariantId or a newVariantName, enforced by a Zod refinement. The second path runs the same find-or-create chain as Quick Add, inside the line's own transaction, so a failed line cannot leave a stray product behind. It exists because requests are Concept-level by design, which means the first order for any new concept has no variant to pick — and before this the form simply dead-ended on an empty list.
